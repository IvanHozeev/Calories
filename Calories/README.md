# CalorieCounter

Простое приложение-счётчик калорий на SwiftUI + SwiftData (iOS 17+), без внешних зависимостей.

## Как запустить
1. В Xcode: File → New → Project → App, назвать `CalorieCounter`, интерфейс SwiftUI. Deployment target — iOS 17.0 или выше (нужно для SwiftData).
2. Заменить сгенерированные файлы `ContentView.swift` и `CalorieCounterApp.swift` на файлы из этой папки, остальные — добавить в проект.
3. Собрать и запустить.

## Что внутри
- **Models.swift** — `Macros` (белки/жиры/углеводы), `FoodEntry` (модель SwiftData — запись о приёме пищи), `MealItem` (черновая позиция до сохранения), `WeightEntry` (модель SwiftData — запись взвешивания), `DaySummary` (вычисляемая сводка по дню), `Sex`/`ActivityLevel`/`Goal`/`UserProfile` (профиль и формула расчёта целевых калорий и белка), `Plan` (премиум-план: срок в неделях, целевой вес, точный расчёт дневной нормы калорий).
- **CalorieStore.swift** — состояние приложения поверх `ModelContext` SwiftData: хранит и синхронизирует записи, пользовательские продукты и записи веса; группировка по дням, суммы БЖУ, хранение и обновление профиля, плана и статуса Premium.
- **ProgressRing.swift** — кольцо прогресса дня.
- **MacrosRow.swift** — переиспользуемый компонент отображения Б/Ж/У.
- **FoodDatabase.swift** — `FoodItem` (модель SwiftData) + база из ~55 встроенных продуктов с калорийностью и БЖУ на 100 г (встроенные продукты не сохраняются в базу, живут только в памяти).
- **FoodQuantityView.swift** — выбор порции (в граммах) для продукта из базы, расчёт калорий и БЖУ на лету, добавляет позицию в черновик приёма пищи (не сохраняет сразу).
- **AddEntryView.swift** — экран сборки приёма пищи: выбор даты, черновой список добавленных позиций с итогом наверху (можно удалять до сохранения), быстрый ввод только калорий (только при выборе прошлой даты — для сегодня продукт нужно указывать явно; в отличие от остальных способов сохраняет **сразу**, объединяя с тем, что уже в черновике, и закрывает экран — без промежуточного шага), подробный ручной ввод (с БЖУ), свои продукты, поиск по встроенной базе — остальные способы добавляют позицию в черновик, а не сохраняют сразу. Кнопка «Сохранить» внизу пишет весь приём пищи в базу **одной записью** (калории и БЖУ суммируются, название — из названий продуктов через запятую). Кнопка «+» в шапке — отдельно, для сохранения нового продукта в свою базу (с БЖУ), это не влияет на текущий черновик.
- **ProfileView.swift** — профиль: пол, вес, рост, возраст, уровень активности, цель (похудение/поддержание/набор массы), норма белка на кг веса. Считает BMR (формула Миффлина-Сан Жеора), TDEE и целевые калории/белок, при сохранении обновляет дневную цель. Под выбором цели (если она не «поддержание») — кнопка «Получить план»: без Premium открывает `PaywallView`, с Premium — `PlanView`.
- **PaywallView.swift** — экран-заглушка оформления Premium: список фич, кнопка «Оформить Premium» просто включает `store.isPremium` — без реальной оплаты (StoreKit не подключён).
- **PlanView.swift** — создание/редактирование плана: целевой вес + срок в неделях, живой расчёт даты окончания, темпа (кг/нед) и точной дневной нормы калорий (через дефицит/профицит от TDEE, ~7700 ккал/кг), предупреждение при слишком агрессивном темпе (>1% веса в неделю). Кнопка завершения плана возвращает дневную цель к обычному расчёту по профилю.
- **ContentView.swift** — главный экран: кольцо, карточка плана (если план активен — прогресс-бар по срокам, вес старт→цель, текущий вес), карточка БЖУ за сегодня с прогресс-баром по белку относительно цели из профиля, баннер-приглашение заполнить профиль (если ещё не заполнен) или взвеситься сегодня (если профиль уже есть, а веса за сегодня нет), статистика, список приёмов пищи с БЖУ каждой записи и удалением.
- **HistoryView.swift** — график калорий за последние 7 дней (Swift Charts) + список дней (последняя неделя показывается всегда, даже пустые дни — можно открыть и добавить записи задним числом).
- **WeeklyChartView.swift** — столбчатый график калорий с линией дневной цели; принимает произвольный список дней и заголовок, используется и в истории, и на экране веса для сравнения с калориями.
- **WeightChartView.swift** — линейный график динамики веса.
- **AddWeightView.swift** — экран быстрой записи взвешивания (вес + дата, по умолчанию сегодня, поле предзаполняется последним весом).
- **WeightView.swift** — экран веса: текущий вес, изменение за выбранный период (7/30/90 дней), график динамики веса и график калорий за тот же период рядом для визуального сравнения (дефицит/профицит vs реальная динамика), список всех записей с удалением свайпом.
- **DayDetailView.swift** — детали конкретного дня: суммарное БЖУ, список записей с удалением, кнопка «+» для добавления записи в этот день.
- **CalorieCounterApp.swift** — создаёт `ModelContainer` для `FoodEntry`/`FoodItem`/`WeightEntry` и `CalorieStore` поверх него.

## Трекинг веса
Отдельная модель `WeightEntry` (SwiftData) — по одной записи на взвешивание. Экран веса (иконка весов в шапке главного экрана) показывает:
- текущий вес и изменение за выбранный период (7/30/90 дней);
- график динамики веса;
- график калорий за тот же период — специально рядом, для визуального сравнения дефицита/профицита с реальной динамикой веса;
- список всех записей с удалением.

Если профиль заполнен, а вес за сегодня ещё не внесён, на главном экране появляется баннер-напоминание. Вес в профиле (используемый в формуле BMR) при этом не синхронизируется с журналом взвешиваний автоматически — это разные вещи: в профиле вес используется для расчёта нормы, в журнале — для отслеживания динамики. Если вес заметно изменился, стоит вручную обновить его в профиле, чтобы пересчиталась цель по калориям.

## Планы (Premium)
Идея: обычная цель в профиле (похудение/поддержание/набор) считает калории по фиксированному множителю к TDEE (±20%/±10%). План — точнее: задаёшь целевой вес и срок в неделях, приложение считает необходимый дефицит/профицит исходя из ~7700 ккал на 1 кг и делает эту цифру дневной целью на весь срок плана.

- Доступно из профиля — кнопка под пикером цели (если цель не «поддержание»).
- `PaywallView` — заглушка Premium: кнопка «Оформить Premium» просто ставит флаг `isPremium = true` в `UserDefaults`, реальной оплаты (StoreKit/App Store Connect) нет. Когда будешь готов подключить настоящую подписку — это единственное место, которое нужно заменить.
- Активный план приоритетнее обычной формулы: пока план запущен, сохранение профиля больше не перезаписывает дневную цель — её продолжает считать план. «Завершить план» в `PlanView` возвращает обычный расчёт по профилю.
- На главном экране, если план активен, — карточка с прогресс-баром по срокам, весом старт→сейчас→цель и статусом (по графику/опережаешь/отстаёшь).
- Есть предупреждение, если запрошенный темп превышает ~1% веса в неделю — это не блокирует сохранение, просто предупреждает.

### Адаптивная сверка (главная ценность плана)
Линейная формула при создании плана — это только стартовый прогноз. Реальный темп почти всегда отличается (адаптация метаболизма, погрешности в подсчёте калорий и т.п.), поэтому `CalorieStore.planAdherence()` регулярно сверяет факт с прогнозом:
- **Ожидаемый вес сегодня** — точка на прямой между стартовым и целевым весом на сегодняшнюю дату.
- **Фактический вес** — не последнее взвешивание «в лоб», а тренд: среднее по последним до 7 записям с начала плана (сглаживает суточный шум — воду, отёки и т.п.).
- **Статус**: по графику / опережаешь / отстаёшь — считается по отклонению факта от ожидания, с порогом (0.3 кг или 5% от всего запланированного изменения, что больше), чтобы не дёргаться от шума.
- Для сверки темпа нужна минимум неделя данных с начала плана (хотя бы 2 взвешивания) — иначе статус «Собираем данные».
- **Прогноз даты цели при текущем факте** — экстраполяция наблюдаемого темпа вперёд.
- **Пересчитанная дневная норма** — сколько калорий нужно есть в оставшиеся дни, чтобы всё-таки успеть к исходной дате плана, учитывая фактический (не прогнозный) вес. Кнопка в `PlanView` применяет это значение как `dailyGoal` одним тапом.
- Если при текущем темпе цель сдвигается больше чем на неделю позже плана — появляется кнопка «Сдвинуть срок плана», которая создаёт обновлённый план с той же датой старта/весами, но новым сроком (`extendPlan(to:)`).

Всё это пересчитывается на лету из уже существующих записей `WeightEntry` — не хранится отдельно.

### Недельный цикл калорий
Многие бодибилдеры едят по дефициту неровно: будни ниже среднего, выходные — рефид. Причины: адаптация метаболизма (лептин/T3 падают на долгом ровном дефиците, периодические более калорийные дни их частично восстанавливают), больше энергии под тяжёлые тренировки в нужные дни, и просто легче соблюдать диету, когда впереди маячит "загрузочный" день. Средняя калорийность за неделю при этом не меняется — меняется только распределение.

- Переключатель «Недельный цикл калорий» в `PlanView`, работает только при активном плане.
- Раскладка по дням недели фиксированная и заранее подобрана так, чтобы **среднее за 7 дней математически точно равнялось** обычной дневной цели плана — `Plan.weeklyCycleOffsets` (Пн…Вс: −8%, −8%, −12%, −8%, −8%, +14%, +30%), сумма смещений равна нулю. Будни чуть ниже среднего, суббота/воскресенье — рефид.
- `Plan.calorieTarget(for:tdee:)` — норма на конкретную дату с учётом цикла; `CalorieStore.effectiveGoal(for:)` — то же самое, но уже с учётом того, есть ли вообще активный план с циклом (иначе просто `dailyGoal`, как раньше). `todayGoal` — то, что показывается в кольце и статистике.
- История/график калорий (`WeeklyChartView`) сравнивают каждый день с его **собственной** целью (влияет на цвет столбца), а не с одним плоским числом — при включённом цикле заголовок графика показывает диапазон цели («500–2860 ккал (цикл)») вместо одной цифры.
- Пока цикл включён, ручное редактирование цели тапом по кольцу отключено — это было бы бессмысленно, цифра всё равно берётся из цикла. Поправки — через `PlanView` (целевой вес/срок).
- Обратная совместимость: `Plan` decode вручную, отсутствие поля `cyclingEnabled` в уже сохранённых планах трактуется как `false`, а не ломает загрузку.

### Историческая цель на день не меняется задним числом
Раньше цель за прошлый день пересчитывалась «вживую» из текущего профиля/плана — если поменять их сегодня, вся история (график, `HistoryView`, `DayDetailView`) перерисовывалась под новую цифру, хотя фактически в тот день действовала другая норма.

- Модель SwiftData `GoalRecord` (date + goal) хранит один снапшот на день.
- `CalorieStore.lockPastGoals()` — как только день перестаёт быть сегодняшним и за него уже есть хотя бы одна запись еды, для него один раз (если снапшота ещё нет) записывается снапшот текущей на тот момент эффективной цели (с учётом плана/цикла, если активны). Вызывается при старте (`init`) и после каждого сохранения (`save()`), так что новый прошедший день фиксируется практически сразу.
- Дни без единой записи еды не фиксируются — фиксировать нечего, и это не тратит место.
- Приватный `CalorieStore.goal(for:)` — сначала смотрит на `GoalRecord` за эту дату, и только если снапшота нет, считает «вживую» через `effectiveGoal(for:)`. Используется в `days`, `pastDays`, `summary(for:)` и, соответственно, во всех графиках/истории. `effectiveGoal(for:)` "вживую" остался только для сегодняшнего дня (`todayGoal`) и для самого создания снапшота.
- Если позже правите профиль/план — уже зафиксированные прошлые дни не меняются, меняется только сегодня и будущее.

## Как считаются цели по калориям и белку
1. BMR (базовый обмен) — формула Миффлина-Сан Жеора: `10×вес + 6.25×рост − 5×возраст (+5 для мужчин / −161 для женщин)`.
2. TDEE (суточный расход) = BMR × коэффициент активности (1.2–1.9 в зависимости от уровня).
3. Целевые калории = TDEE × коэффициент цели: похудение ×0.8 (дефицит 20%), поддержание ×1.0, набор массы ×1.1 (профицит 10%).
4. Целевой белок = вес × норма г/кг (по умолчанию 1.7, можно менять в профиле).

При сохранении профиля дневная цель по калориям на главном экране автоматически обновляется на посчитанное значение (её всё ещё можно поменять вручную тапом по кольцу). Белок отслеживается отдельно — карточка БЖУ показывает потреблённое сегодня и прогресс-бар к цели.

## Хранение данных
Раньше — ручной JSON в `UserDefaults`. Теперь — SwiftData (SQLite под капотом): нормальная схема, запросы по дате через `FetchDescriptor`, не нужно перечитывать/переписывать весь массив при каждом изменении. `dailyGoal` (число) остался в `UserDefaults` — для одного значения так проще.

Важно: данные всё ещё живут в контейнере конкретной установки приложения на конкретном устройстве/симуляторе. Если пересоздать Xcode-проект с другим bundle identifier, удалить приложение перед переустановкой или сделать Erase All Content and Settings в симуляторе — это будет для системы новое приложение с пустой базой, независимо от того, UserDefaults это или SwiftData. Чтобы данные переживали переустановки и синхронизировались между устройствами, нужен отдельный шаг — SwiftData + CloudKit.

## Как работает переход на новый день
Каждая запись хранит точную дату и время. «Сегодня» — это записи, у которых `Calendar.isDateInToday` истинно; всё остальное автоматически попадает в историю. Дополнительной логики "сброса" не требуется — как только наступает полночь, вчерашние записи сами уходят в историю, а счётчик сегодняшнего дня стартует с нуля.
